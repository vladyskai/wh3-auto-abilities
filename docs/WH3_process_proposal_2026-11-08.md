# A better loop for the mod (proposal, 2026-11-08)

Nothing here is decided yet. It is a proposal for the user to amend or approve.

## 1. What goes wrong today

- Abilities are taken in whatever order a conversation reaches them. There is no fixed checklist that
  makes a trigger use the best read the mod has.
- Triggers are designed with the reads available at the time and are never re-checked when a new read
  arrives. Round 131 found 10 shooting buffs still riding the melee trigger, written before the
  firing flag existed.
- "Done" means "built and the test suite passes". Nothing records whether an ability really fired in a
  battle, did what it should, and was worth it. 245 of 752 automated abilities have fired at least once
  in a real battle; the other 507 are unproven.

## 2. Every ability climbs one ladder

| Step | Name | Who | Proof |
|---|---|---|---|
| 1 | Open | | the survey lists it |
| 2 | Proposed | Claude | a dossier plus 2 or 3 trigger options |
| 3 | Approved | the user | the ruling, quoted in the tracker |
| 4 | Built | Claude | the harness: positive, negative and edge worlds |
| 5 | QA passed | Claude, in game | a QA battle log shows: armed, trigger reason, ACCEPTED, the effect seen, no unwanted move order |
| 6 | Field approved | the user | a real campaign battle, and the user's verdict that it is useful |

Any step can send an ability back to step 2. The progress page (`docs/progress.html`, rebuilt by
`tools/make_progress_page.py`) will show this ladder once the tracker records steps 5 and 6.

## 3. The round, step by step

1. **Pick a batch** of 5 to 15 abilities from one survey group, or one trigger family.
2. **Dossier, generated by a tool** (new): for each ability, the effect stats, targets, range, duration,
   uses and recharge, who carries it, the current status, and every earlier decision from the tracker.
   No hand-copying, so nothing is missed (rule 11).
3. **The sensor checklist** (new). Every proposal walks the same list of what the mod can read, and
   says which read it uses and why the others do not fit:
   - **the unit itself:** melee, charge, health, morale/wavering, fatigue, routing, moving;
   - **shooting:** the firing flag and cast point, ammunition, missile range, its current target
     (in melee, hidden, in range);
   - **allies and enemies:** distance, class (infantry, commander, large, missile, beast...), health,
     in melee, under fire, barrier;
   - **the screen:** selection and the ability button.

   The rule: use the read that matches the moment the effect pays off; reuse an existing family when
   it fits; add a new family only when it clearly does better. Two or three options, one
   recommendation.
4. **Your ruling** on the whole batch at once (one questionnaire).
5. **Build:** source, annotated copy, harness section, RED control, full suite, build, install, archive.
6. **QA battle** (new): a short scripted test battle per batch, checked by a tool that reads the log
   and prints PASS / FAIL per ability (section 4).
7. **Your field test,** and your verdict per ability: useful, not useful, or wrong moment.
8. **Close:** tracker, database, workbook, the progress page, one commit and push.

**Once:** an audit of the 752 automated abilities against the sensor checklist, done by a tool from the
game data. Example: a missile stat on a melee trigger, or a speed debuff on a trigger with a missile
arm. The audit lists the mismatches; you rule on them as one batch.

## 4. Can Claude test in the game?

**Yes, as a smoke test, if it is built the right way.**

Watching the battle and reacting in real time would not work well. Screenshots are single snapshots,
each action takes seconds, and a battle moves faster than that. But the battle does not need to be
watched: the mod's own log already records every trigger reason, every cast and the game's answer.
The log is the proof, not the picture.

So the work splits in three:

- **A QA mode in the mod** (a separate test build): on battle start it arms every ability the player's
  army owns and orders the army to attack, through the same script controls the mod already uses.
  Nobody has to click badges or give orders during the battle.
- **Claude drives the menus only:** start the game, open Custom Battle, pick the armies from the QA
  plan, start the battle, wait, quit. Menus are still screens, which desktop control handles. The game
  should run in borderless windowed mode: a fullscreen game can show as a black screenshot.
- **A log checker** prints PASS / FAIL per ability for the QA battle.

**Limits, said plainly:**

- Setting up a custom battle by clicking could take 10 to 20 minutes the first time. If the custom
  battle screen can save and reload an army, it gets much faster (to be checked in the first trial).
- Some abilities come from campaign skills or items that custom battle may not offer.
- Some triggers need a situation a short battle may not produce: low ammunition, a wavering ally, an
  enemy just out of range.
- Whether the game accepts clicks sent by desktop control is unknown until tried.

QA catches "does not fire", "fires on the wrong target", "the game refuses it" and "it walks the
caster". It does not judge usefulness: that stays your field test (step 7).

## 5. The minimum QA set

Not every ability needs its own battle. The trigger code is shared per family, so QA needs one
ability per combination of:

- **trigger family** (52);
- **cast form:** self, ally unit, ally ground, enemy unit, enemy ground, ground at the caster, summon;
- **gates:** a multi-use charge hold, a wind-up, two abilities on one caster.

A tool can pick the units that cover all of these in the fewest armies (a set-cover over the game's
own unit-to-ability tables). The expected result is a handful of armies, not hundreds of battles.
Then each new batch only adds a QA check for what it changes.

## 6. The trial (2026-11-08): what worked

Claude launched the game through Steam and the Total War launcher (game version 9.0.5) and reached the
main menu.

| Input | Result |
|---|---|
| Screenshots of the game (windowed) | **work**, clear and readable |
| Mouse movement | **works**: buttons light up and tooltips appear |
| Keyboard | **works**: Escape opened and closed the quit dialog |
| Mouse clicks | **ignored**: no button reacts, on any screen (a normal, slow press-and-release and a double click all failed; the game was focused and is not running as administrator) |

**Consequence:** Claude cannot click through Custom Battle setup today. The realistic QA loop is: the
user sets up a QA custom battle once and saves the armies (a few minutes); the QA build of the mod arms
everything and orders the attack by itself; Claude reads the log and prints PASS / FAIL. If a later
version of the desktop driver sends clicks the game accepts, Claude can take over the menus too.
