# Proposal (round 126, not implemented): the firing flag from the game's reload table

Status: proposal for the user's ruling, 2026-11-03. Nothing in the mod has changed.

## The user's idea

Use each unit's base firing rate from the game's tables. The first shot of an episode can't be
anticipated, so the cast of a firing-boosting ability goes in between the first and second shot,
"maybe in the middle": first shot + half the base reload. In-battle improvements (tech, skills,
abilities) usually make reload faster, not slower, so half the base rate is very likely still
before the second shot.

## What the game data gives

- **Coverage:** a base reload time exists for every ranged land unit: 535 units, 0 broken links.
  The chain is: land unit -> its missile weapon (or, for artillery, its engine's weapon) ->
  projectile -> `base_reload_time`.
- **Typical values:** 4 to 25 s, mostly 8 to 13 s.
- **Extraction:** regenerated from the installed game by `tools\extract_gamedata.py` (new tables:
  `land_units`, `missile_weapons`, `projectiles`, `battlefield_engines`).
- **Reload skill:** 89 units carry a non-zero reload-skill stat. Its exact effect on reload time is
  not confirmed, so the proposal does not use it (see open point 3).

## Checked against the 2026-11-03 battle

| Unit | Base reload | Cast point (half) | OFF window (1.25 x base) | Firing episodes |
|---|---:|---:|---:|---:|
| Crossbowmen x2 | 13 s | +6.5 s | 16.25 s | 1 each |
| Handgunners x2 | 13 s | +6.5 s | 16.25 s | 1 each |
| Mortar | 19 s | +9.5 s | 23.75 s | 1 |
| Helstorm | 17 s | +8.5 s | 21.25 s | 1 |

Using the table for the OFF window fixes every flicker the round-125 rule showed (23 episodes on
the Helstorm, 10 on the Mortar): one steady episode per unit for the whole battle.

**A caveat about "the second shot".** Units do not fire as one gun. Infantry models fire one after
another (10 to 12 drops in the first 3 s), and the Mortar and Helstorm have 4 engines each (88 =
4 x 22, 264 = 4 x 66). Unit-level ammo therefore drops almost continuously, and no single "second
shot" is visible in the log. What half the base reload guarantees is that the buff lands before the
models that fired first can fire again. The models that fired later in the first volley also
reload, so they shoot again at most a few seconds after that, all inside the buff.

## Open points for the user

1. **Rule 4 ("no baked stats").** A reload table generated from the game's own data is a stat read
   from tables, not live from the engine. There is no live reload read in the battle API. This
   needs the user's explicit exception. It is narrow: the table is regenerated by a tool, never
   hand-typed, and used only as an upper bound.
2. **Predicting the first shot.** A missile unit whose current target is within its own live
   `missile_range()` (and which has ammunition) is about to shoot, or is shooting. If that moment
   reliably comes before the first ammo drop, a cast could land before the first shot. The engine
   gives no "is shooting" read, so this is a predictor, not a fact. Proposal: log that moment in the
   next probe round, measure its lead over the first drop in a real battle, and decide from the numbers.
3. **Reload skill.** For the 89 units with reload skill, half the base may come later than their
   true half. Option: confirm the formula first, or accept it (still during firing, just later).
