## Engine and API traps

Read `references/cast-orders-and-aim.md` before writing a cast, summon or
enemy-targeting trigger: order replacement and per-unit serialisation, charge gates,
edge-to-edge distance, motion reads and the aim dials.

Read `references/engine-api-traps.md` before writing any trigger: the ground plane is
X/Z (`get_y` is HEIGHT), `HealthPercent` is a 0..1 fraction, `unit_distance` is
edge-to-edge with no radius read anywhere, multi-use abilities answer `can_perform=true`
with an empty pool, and a second `perform_special_ability` in the same tick REPLACES the
first (order semantics) so gates must be per-ability wind-up AND per-caster.

Log forensics: `references/log-forensics.md`. Wheel-scope gates (army-bar can never cast) and
the light-vs-full verification cadence: `references/scope-and-verification.md`.

## Standing build rules (user-set: apply, never re-ask)

- EVERY trigger range constant is 70% of the ability's real range, floored to whole metres
  (`FOURTH.RANGE_FRACTION = 0.70`; `target_intercept_range` IS the cast range, `effect_range` is the
  effect's area radius, 0 = self-only). The build asserts `constant == floor(real*0.70)`. The rule is
  absolute - it overruled a field-tuned 25 m value the user had set earlier himself.
- NEVER gate an offer/range test on `battle_unit:unit_in_range()`: it is the engine's own much looser
  read (it passed at 81.3 m where the ability's bound was 52 m) and trusting it makes the engine WALK
  the caster to the target - which the user reports as an unwanted move order. Compare `unit_distance`
  (edge-to-edge, bounding-box aware) against your own constant ONLY.
- `unit_distance` is EDGE-TO-EDGE on bounding boxes, so it cannot answer "is A directly under B": two
  large formations can sit with box edges 0.5 m apart while their CENTRES are 15 m apart, and any
  small metre bound then fires with nothing underneath (the reported "releases too soon"). For an
  overlap/underfoot test use HORIZONTAL CENTRE distance between the two `position()` vectors (x/y
  through `get_x()`/`get_y()`; never 3D - a flier's altitude makes every drop read far) against the
  sum of both radii times a stated fraction, or, when no radius read exists, ONE documented constant
  standing in for the formation footprint. Log the centre distance AND the threshold every time so
  the user can see why it did or did not fire. A user-chosen metre value here deliberately overrides
  the 70% rule - keep it a single named constant, exempt the evaluator from the 70% map explicitly
  (an evaluator-identity check, or the range map re-bounds it), and comment it as a test value.
- Cast targets: enemy-targeted abilities cast at the ENEMY, ally-targeted at the chosen ALLY, never the
  owner; enemy and ally handles are RE-FETCHED from the script-unit enumerators on the same tick as the
  cast (a controller handle held from an earlier poll returns accepted=true, consumes no cooldown and
  applies nothing). Army-bar keys (`army_abilities`) are skipped outright; the M/A badge is the opt-in
  that makes a risky ability acceptable to ship enabled.
  Evidence, probe patterns and depth: `references/enemy-targeting-and-range.md`.
- SCOPE (current, supersedes every earlier exclusion rule): implement ONLY abilities on a unit's
  ability wheel. Spells and army-bar abilities fall outside implicitly; everything else is in scope.
  Define "in wheel" from the DATA, not from key names: carrier `unit_abilities.source_type` in the
  unit-side set (active/bound/lord/character/unit/item/rune/weapon), drawable (`icon_name` set,
  `is_hidden_in_ui=false`, a `unit_special_abilities` row), and not in the spell/cataclysm/army/quest
  families. Roster junctions alone are NOT sufficient - most working keys are item/weapon-granted and
  have no roster row. Method and counts: `references/summons.md`.
- An ability granted only to a `_boss` unit is out of reach. Verify boss-only from the grant junctions
  plus the unit's attribute group and multiplayer cap: a `_boss` substring in a key is NOT proof -
  `*_big_boss*` keys are ordinary recruitable Big Boss heroes.
- Re-read EVERY exclusion rule against what the mod can do NOW before trusting it. Rules written when
  enemy targeting, ground casts and real cast ranges were unavailable go stale and hide hundreds of
  abilities (one review refuted 281 of them). Report excluded totals by FAMILY SIZE - how many rows the
  family holds - never by which rule claimed a row first.
- The user reserves trigger design for himself: give the mechanism and 2-3 trigger options with the
  evidence for each, state a recommendation, then WAIT for approval. Do not pick a trigger and ship it
  because it looks obviously right.
- The master spreadsheet is his single source of truth: `docs\WH3_abilities_master_v<N>_<date>.xlsx`
  (+ `.ods`), a NEW FILENAME per change with a Changelog row, and a Definitions sheet carrying the
  scope rule, the status vocabulary and the trigger-family glossary. Never overwrite an older version.
  Its trigger column is derived per evaluator FROM THE SOURCE, every check in order - not paraphrased.
  Verify each new version by RE-OPENING it from disk: the same data-row count as the previous version,
  every changed ability showing its new trigger text, and the Numbers sheet reconciling to the tracker.
  Silent loss is real here - openpyxl's `insert_rows` does not move merged ranges, so an inserted row
  can swallow its own writes without raising. Whatever the workbook answers, put the substance in the
  chat reply as well: he reads the chat, and an attachment alone is not a deliverable for him.

## Mock-harness conventions

- Mocks provide `bm` (repeat_callback/repeat_real_callback/register_phase_change_callback/
  is_conflict_phase/get_scriptunits_*/command handler/`get_current_phase_name`), `core`
  (get_ui_root/add_listener), `UIComponent` (raise for number/string/boolean, pass nil through),
  `common.get_localised_string`, `is_string`, `find_uicomponent`; log output goes to an
  `out_lines` table via a global `out(s)`.
- Assert with substring helpers: `l:find(t, 1, true)`, count with `#find(t)`; exact `== n`
  counts only for lines the round's fix guarantees (a `>=` for transition lines is safer).
- Hostile-VALUE quirk (dressed-string keys): model the key as a table with `__tostring` + `__concat` (the copy path works) whose raw `string.lower`/`string.find`/`string.len`/`#` blow up; wrap those three `string.*` functions and `__len` to COUNT every direct raw use (concat stays allowed, uncounted) and assert the count is 0 at the end. Prove the fixture in a control section (raw ops raise; tostring/`..` work), then reset the counter so any later count is the mod's.
- Model the engine quirk the round is about AND include a control check that the quirk has the
  in-game shape (e.g. poisoned `string.len`, `bm:` returning a boolean, a stale handle whose
  every method raises).
- Script-side engine reads are all pcall'd, so mock methods may raise freely — an escaping
  error is exactly what a harness must catch.
- Fixture state a world must CHANGE mid-run (a card's CurrentState, a bar key) needs a handle
  from the builder: keep a by-id component map (`W.card_comps[id] = c`) and flip the field the
  mock reads dynamically (`c.state = "selected"`) — never rebuild the world to change one value.
- A periodic sweep that logs only on change should dedupe by note TEXT (a last-note variable)
  and be tested directly: repeated identical sweeps -> no repeat line; each change -> exactly
  one line; change-back -> one more. Prove a sweep's override of a click fast-path with a
  world where the click sets a value the engine disagrees with (expect exactly one
  `... updated from card states: <old> -> <new>`).
- Splitting a sweep into a fast (every ui tick) path + a slow (1/s) census: share ONE reader
  and ONE derivation between the two, make the fast path silent on no change, TICK-STAMP its
  change header (`... (tick N)` using tick_count) and include the per-card lines once on a
  change. Consequences for old harnesses: the census' own adoption line becomes effectively
  dead (fast path wins) and per-card line counts double on a change tick - old `== 1` counts
  are designed deltas. New harness proof shape: capture #out_lines, flip a card's state in
  the by-id card map, call ui() exactly once, and assert the exact (filtered, see below)
  block: header with `(tick N)` + both letter lines + the card lines.
- Mock-run exact-block/silence assertions must FILTER the ambient `bisect: step` lines: the
  CLAIM_BISECT ladder logs a capped run (6 lines per ability per ui tick) while its
  per-battle budget lasts, so even 'nothing changed' tick runs are not line-clean. Filter
  with `raw_find(l, "bisect: step", 1, true)` in block comparisons and silence counts, and
  print the filtered count in the check label so the filter stays honest.
- The ui tick interval is the `bm:repeat_real_callback(ui_tick, 50, ...)` registration value,
  and the API's interval argument is MILLISECONDS (battle_manager:repeat_real_callback) -
  so the fast path's worst-case latency is one ui tick, ~50 ms. The in-file `ui timer is
  running (real callback, 500 ms)` log text is stale; do not trust it or the README's
  '(500 ms)' prose for the cadence.
- Vanilla-proven interval semantics (extract `script/_lib/lib_timer_manager.lua` from
  data_script.pack over the RPFM WebSocket: OpenPackFiles -> GetPackFileDataForTreeView ->
  ExtractPackedFiles): model timers are ms in battle (s in campaign), real timers are ms in
  ALL modes - but real timers are UI-update driven with VARIABLE resolution that 'can be
  greater than a model tick (100-200ms)', so 50 ms is the REQUESTED interval, not a latency
  guarantee. When a user-visible flip must not wait at all, drive it from the event handler
  itself (the card-click synchronous refresh) and log the tick, so the battle log can prove
  which clicks landed in-handler. A reported ~0.5 s latency is NOT a registration in this
  file ('500 ms' exists only as stale text): check event delivery instead - count click-path
  lines vs fast-path '(tick N)' adoptions without click lines in the session log.
- lupa runs Lua 5.5 here: pairs() order over string keys VARIES between processes (per-state hash seed) though it is stable within one. A fixture whose outcome depends on the mod's table iteration order (e.g. which wanted ids survive a >cap unit list) must CALIBRATE at runtime: build a mirror table with the same keys inserted in the same sequence the mod inserts them, read ITS pairs() order, pick the fixture ids from that order, and validate the mirror in the same run against observed mod behavior (which mock cards its sweep actually read). Never hardcode a drop set - and re-run the harness in fresh processes to prove the adaptation.
- Visited-node metrics: give every mock component per-method call counters; reset, then run exactly ONE ui tick at steady state (no poll => tick_count frozen, census gate closed, claims done) and sum Id() reads over the panel subtree. Cap 12 vs 40 gave IDENTICAL walk reads (19/sweep) - the cap only truncates the wanted-id collection (card state reads 12 -> 16).
- Counting the HUD walk (the blind-walk class of fix): the mod calls
  `core:get_ui_root():Find("hud_battle")` exactly once per find_ability_buttons
  and nowhere else, so increment a counter in the mock root's Find for
  `what == "hud_battle"` and that IS the walk count (it also counts a walk
  that finds no hud). Mirror the mod's `ui_ticks` with a harness counter
  bumped once per ui() call (the mod increments at the top of the tick, so
  they stay equal) - then compute the EXACT expected cadence analytically
  (`count of t in (t0,t1] with t % mod == 0`) instead of hardcoding, because
  the gate's `% 2` / `% 4` / `% 100` alignment is otherwise unknowable from
  outside. A gate world that changes the selection must land the change tick
  on an ODD ui tick (run one extra ui if ui_calls is odd) - the pre-edit
  every-2nd-tick gate walks only on EVEN ticks, so the fix's 'selection
  change -> exactly one walk' discriminates cleanly (old 0, new 1). A world
  that leaves NOTHING selected stays in the mod's bootstrap branch (walk every
  2 ticks) forever - select a known unit before the window when the assertion
  is about the safety net, or the tail will show the bootstrap cadence.
- Counting the walk's LOG volume directly from the live build: `log_lines`
  already holds every line, so `count_log(W, "scan done:")` before/after a
  window measures the log bloat the blind walk produced (green 5 vs pre-edit
  250 over the same 500 ticks = the ~50x collapse). Model-free, no new mock.
- Measuring a per-tick/per-pass metric the mod computes in ONE named function (e.g. "the ui tick's per-ability work"): wrap the global `ipairs` and count a marker-table iteration ONLY when `debug.getinfo(2, "f").func == <that function>`, with the reference captured from the timer registration (`bm:repeat_real_callback(fn,...)` -> `W.ui_fn`; set it in `load_world` after the load). A length-based counter alone is WRONG: the mod's `ability_for`/`ability_for_badge` marker->entry lookups ALSO iterate the full ABILITIES table (1-3 steps each), as do `all_buttons_found()` and `selected_unit_owns_unclaimed_key()`, so a raw count of full-table iterations includes them and never collapses. `debug.getinfo(2).name` is NOT usable - a function invoked through `pcall(W.ui_fn)` reports name=nil - compare the function OBJECT instead. Reference numbers (3 abilities, 2 loops = build + show/hide): green active set of 1 -> 2 iterations per pass (1 ability per loop), red control -> 6 (3 per loop); the full-table bootstrap is 6 either way, so a bootstrap world is a guard, not a discriminator.
- A round that changes CARD_SWEEP_MAX's VALUE (or any static text the older suites pin) flips exactly ONE stale static gate per older harness (46-52 here: 'the sweep is gated ... caps at 12 cards' / 'the verbose census keeps ... its cap'). Diff pre/post runs and classify that single named line as the round's designed delta; never edit old harnesses.

## Pitfalls

- Workbook inventory: status vs status reason, the orphan-key audit and the same-unit numbers rule - `references/inventory-status-gates.md`.

- Nested arming tables + guard (item 2.1): the per-(unit,marker) arming switch is `armed[ui_id][marker]` and the one-attempt brake is `last_attempt_at[ui_id][marker]`, both keyed by the ui id AS A NUMBER. The read is `local per = armed[ui_id]; return per ~= nil and per[marker] == true` (a miss never builds the inner table), the write builds the inner table only on an actual flip, and the only remaining log line is the unchanged `AUTO <marker> for unit <id>: now <ON|OFF>`. `armed` is never explicitly cleared - it is a chunk-local `{}` allocated once at load (a fresh battle reloads the script), and dropped units simply become unreachable; keep that (no reset call).

- Crash-hunt bisect ladder (when a crash hides between two log lines): ship a numbered switch (e.g. `CLAIM_BISECT`, one enabled-op count) that gates each engine-value operation on its own, bracketed by `bisect: step <n> <name> entering` / `ok` lines (`SKIPPED (disabled)` when off, `FAILED: <err>` instead of `ok` when a pcall caught the error). Default ships only the steps the header already proved safe; raise ONE per battle; the killer is the step whose `entering` line is the log's last line with no `ok`. Cap each step's lines per battle (e.g. 40) with a one-off suppression note, or a per-component scan floods the log; and make disabled steps fall the verdict back to 'not ours' so the walk keeps going.
- At an intermediate bisect level the mod deliberately does NOT claim (the verdict gate is off) - harness worlds below full level must assert "no claim + skips named", and test "claim lands" either at full level or with a single poisoned step whose fallback path recovers (e.g. poison `string.lower` with a substring match, then prove step 6 FAILED -> step 7 finds -> claim lands).
- MULTI-USE abilities (`unit_spec_abil.num_uses` > 1) are NOT braked by the engine: `can_perform_special_ability` answers TRUE with the pool EMPTY and `perform_special_ability` is ACCEPTED (55 accepted casts of a 3-use/90 s row in 108 s, its button greyed 'selected_inactive' throughout), so the 2 s guard re-spends the same pool forever and the charge counter loops 3-2-1-3. Single-use rows DO get the 'does not support this special ability' refusal. Any auto-fire on a multi-use row needs a data-derived hold: after a successful cast, hold the pair for its own `recharge_time` (one use per cycle; the pool never drains, no cast is swallowed). `recharge_time` is per-use and independent when `shared_recharge_time` = -1 - proved by the three uses coming back exactly 90 s after each of the three casts (67/69/71 -> 157/159/161).
- `perform_special_ability` issues an ORDER, not a fire-and-forget effect: re-issuing it while the previous cast is still inside its `wind_up_time` REPLACES the pending order, so a guard shorter than the wind-up makes an ability cancel itself forever. Symptoms are a charge counter looping 3-2-1-3 with nothing spawning, or an ability that "starts" every couple of seconds and never lands. Wind-up is data (`wind_up_time` on the ability row, commonly 2-5 s; there is no `cast_time` and activation phases are usually empty), so derive a per-key in-flight hold of `wind_up + 2 s`, never below the ordinary 2 s guard, and generate the table from the data rather than hand-listing keys. It is ADDITIVE to the multi-use charge gate - the two catch different failures and overlap on only part of the roster (50 of 225 keys), so never trade one for the other.
- The engine allows only ONE special ability in flight per unit: two DIFFERENT abilities on the same caster in the same tick both return accepted=true, and the second REPLACES the first mid-wind-up - the first use is spent and its effect never lands (its next attempt is a whole recharge away) while the second survives. Nothing in the data explains it (no shared `recharge_time`, no cooldown group, no parent, no exclusivity column), so model it as an engine rule. Fix with a PER-CASTER serialisation window after any successful cast: no different ability on that unit for `wind_up + 2 s`, floored at ~2.5 s, the fired ability keeping its own pair gates. A same-ability repeat must NOT extend the window or one trigger starves the other forever. Harness proof: two ready abilities on one caster -> first fires, second logs the gate and fires one window later; the red control fires both in the same tick.
- `CcoBattleUnit.HealthPercent` (via `common.get_context_value`) is a FRACTION 0..1, NOT 0-100: every `hp < N` threshold silently becomes 'always true' (336 field picks printed only `health=0%`/`health=1%` while the picked unit fought on for 84 s, and a live unit once read 0%). The game's own `unit_banner.twui.xml` feeds the field into a `ContextFillBar` and tests `HealthPercent < 1`. Use `battle_unit:unary_hitpoints()` (API dump: 'expressed as a unary fraction ... 0.75 = lost 25%') with a 0..1 -> x100 scale on the context fallback; a fraction read against a percent threshold also breaks every ≤75% heal gate at once, so route ALL health consumers through ONE reader.
- ALLY-REACHING HEALS must not be gated on the OWNER's health. An area heal that reaches allies fires when the CASTER **or** a hurt ally inside its `effect_range * 0.70` is below the threshold: pick the LOWEST-health one and cast at the ground under that ALLY (`target_ground_under_allies`), or in unit form on the ally where the ability takes a unit target. Owner-only stays correct for a heal whose text says '(to self)', for a target-class gate the mod cannot read, and for one that reaches allies but has `effect_range 0` with no range column - a guessed distance test is worse than under-firing.
- 'NOT A LORD OR HERO' is a READ, never a name guess: derive the key set from `land_units.class == "com"` union `main_units.caste` in {lord, hero} (1,409 keys game-wide), match by exact whole-key equality on `battle_unit:type()`, fall back to `battle_unit:unit_class() == "com"`, and FAIL CLOSED when neither answers. The game's own target-restriction flags (`unit_is_commander_class`) corroborate the derivation. Same rule for other classes, but check the dump FIRST for a dedicated predicate: `battle_unit:is_infantry()` and `battle_unit:is_currently_flying()` are REAL reads needing no derived set, with `unit_class()` as corroboration - derive a key set only when no predicate exists.
- When the user reports 'the ENGINE allowed it' (e.g. a 20%-health finisher firing on a healthy unit), check OUR read scale before hunting for a CA bug: the one field report of that shape was the 0..1 `HealthPercent` bug, and eighteen searches for prior art found nothing because there was no game bug.
- Harness fixture/arming controls must run with the mock's crash-log writer DISARMED (`armed=false`): a control that deliberately blows the fixture up otherwise leaves its sentinel lines in the captured log and fails the mod's own "no blow-up in its log" hygiene checks. Reset the counted-uses counters after the control, before the mod runs.
- Script variants generated by harness code via Lua `io.write` on Windows come out CRLF; normalize (`tr -d '\r'`) before diffing a variant against the source to prove a one-line patch. The shipped source itself must stay LF - only variants are throwaway.
- Editing a SHIPPED .lua with Python text mode (`io.open(p, "w", encoding="utf-8")`) silently flips every `\n` to CRLF on Windows, and `build_and_install.py`'s UI-probe gate (`ui_raw == ui_probe_txt.encode("utf-8")`, source read in TEXT mode => LF) then fails with `packed and byte-identical to source : False` while the per-file sha256 gate still prints `MATCHES SOURCE: True` (both sides CRLF) - a confusing split. Read/write shipped Lua in BINARY (`open(p,"rb")` / `open(p,"wb")`) or pass `newline=""`, and after any scripted edit assert `open(p,'rb').read().count(b'\r') == 0`. Diagnose the mismatch by printing `len()` + sha256 of both sides and the first differing byte.

- Converting composite-string table keys (`t[id.."|"..marker]`) to NESTED tables (`t[id][marker]`) silently breaks arming when the two writers of the SAME pair carry the id at DIFFERENT types: the read side gets the engine's `unit:unique_ui_id()` (a NUMBER) while the click paths carry the SAME id as TEXT (selected_ui_ids is built with `tostring(ui_id)`, the card id is the same number in string form). `t[1001]` and `t["1001"]` are different slots, so the read never sees the write and the unit silently stops firing - the old composite key hid the mismatch because `tostring` normalised both. Normalise at the boundary with an allocation-free `local function unit_slot(id) local n = tonumber(id); if n ~= nil then return n end return id end` used at EVERY site (number passes straight through, numeric text maps back, a non-numeric id stays itself), keep the read shape two-step (`local per = armed[ui_id]; return per ~= nil and per[marker] == true`) so a miss allocates nothing, and let the older harnesses' arming worlds be the oracle: they pass only if the number/text normalisation is right.
- Reaching the mod's PRIVATE locals from a harness (to assert a table's internal shape): walk the upvalue graph with `debug.getupvalue` from a callback the mod registered, matching by upvalue NAME (`local function find(t,f,name)...` BFS with a seen-set), and grab the table via `debug.getupvalue`. `armed` is reachable from the ui-tick callback but the guard table (`last_attempt_at`) lives ONLY in the poll body - which the `pcall` hook captures as `POLL_BODY_FN` on the FIRST poll - so a world that must read the guard HAS to poll once before grabbing (or the grab returns nil).
- Red-control assertions that index a nested slot (`t[uid][marker]`) CRASH the whole harness against the pre-edit build (`attempt to index a nil value`) and abort every later check, instead of failing cleanly - use a nil-safe reader gated on the slot (`local function slot(t,id,m) local p=t[id]; return p~=nil and p[m] or nil end`) and compare to `true`/`false`/`nil`, so the pre-edit run reports exactly the round's FAIL lines and nothing else.
- Harness counters count WORLD RUNS PER FILE (each world is run for the live source AND the annotated copy), so an EXPECTED tally is `worlds x 2` - a fresh round that tallies `worlds` will fail its own count check (e.g. N_OK 8 vs a hardcoded 4). not log checks - point one harness at the copy, record every `uc:perform_special_ability(k, u)` into `W.fires` (assert per-key/per-unit counts) and record badge `SetText`/`Layout`/`SetDockOffset`/`SetDockingPoint` calls on the created components; exclude log-text assertions entirely. Ban the substrings `log(` and `string.find` from the WHOLE copy INCLUDING COMMENTS (comment prose mentioning them still trips the parent's grep), and diff the `local function` inventories source-vs-copy to prove every functional function survived and only ladder/probe/dial/inventory/console helpers were dropped. Re-run lupa syntax + the recorder harness after every later comment pass.

- The engine can dress a value as a string: the ability-key value passed `type(key) == "string"` and printed fine through `..` (the walk header), yet sessions crashed right AFTER `ability button: key='...'` with no claim line ever — the only work there is string.lower/string.find on that value. - A world that must observe the POLL's main loop (re-lists, the 60 s fallback, per-unit rescans, the dead-unit drop) MUST set `W.conflict = true` AFTER `deploy_phases` - `deploy_phases` leaves `conflict=false`, and every poll then returns at `if not bm:is_conflict_phase() then return end` BEFORE the per-unit loop, so a world expecting rescans/drops sees none and its counts read 0. The `Deployed` phase callback still builds the watch list, so the failure is easy to miss.
- Counting CALLS of a mod function that walks a marker table: the established idiom is an `ipairs` wrapper keyed on `debug.getinfo(2,"f").func == FN`; one full call of a two-loop function costs `2 * #ABILITIES` marker steps, so derive calls = steps / (2 * #ABILITIES) and print both. Keep the whole set of such counters in ONE main-chunk table (`local OHNN = { fn=nil, iters=0 }`) - a bare `local FN`/`local N` pair risks the main chunk's 200-local ceiling.
- "Every LIVE world fails `the file loads` while the annotated copy loads fine" = the live source hit Lua's 200-local ceiling at COMPILE time: `loadfile` returned nil + message (e.g. `too many local variables (limit is 200) in main function`) and the harness's `assert(loadfile(path))()` threw it away with no text. - Foe-Seeker fatigue trigger (approved): the API dump HAS a plain getter `battle_unit:fatigue_state()` - documented values `threshold_fresh` / `threshold_active` / `threshold_winded` / `threshold_tired` / `threshold_very_tired` / `threshold_exhausted`, a plain engine enum (NOT the wheel's localised FatigueName, so nothing localisation-dependent is parsed). ## Roster expansion at scale (the questionnaire trap)

- Asking the user about abilities five at a time does not scale: ~800 candidates took ~30 user sittings and felt like no progress. The bottleneck is the QUESTION COUNT, not the build (~13 min per round regardless of size), so widen the rules before adding blocks.
- WIDENED AUTO-RULES are the lever. Written as numbered standing rules in the tracker legend, in terms of EFFECT FAMILIES not wiki prose, so a classifier can apply them mechanically: positive-only self/ally buffs -> auto-accept with the trigger chosen by family (melee/armour/resistance/leadership -> in-melee self; heal-per-second alone -> health<=75 no melee gate; heal + armour/defence -> melee AND health<=75; Unbreakable/Cannot Die -> wavering self, or self-or-ally in range when it reaches allies; charge bonus/charge speed/mass -> charge and in-melee); enemy debuffs (negative stats to enemies in range) -> auto-accept as in-melee self; clear unsuitable families (vortex, bombardment, summon, movement-only, no sourceable effect text) -> auto-exclude with a reason; rampage, friendly fire, mutual exclusivity, army-bar, stealth/escape, transform, enemy-read-dependent and mixed cases -> flag for the user. This took 999 undecided rows to 327 auto-accepted / 325 excluded / 347 flagged in one 6-minute sweep.
- Classify from the GAME'S OWN DATA, not wiki guesses: effect family from `grouped2.json`, engine flags from `unit_spec_abil.tsv`, real effect phases (`phase_junc.tsv` + `phases.tsv`) for negative/friendly-fire/mixed detection. Keep the classifier and report-generator as separate reproducible scripts so the provenance of every status is recoverable.
- Deliver the sweep as a print-friendly report file with a count table plus appendices (auto-accepted by trigger / excluded with reason / flagged with reason), so the user vetoes in ONE pass instead of answering forms. The flag list is then the only remaining queue.
- A bulk append rides EXISTING evaluators and is mostly a data diff: 327 abilities landed on three evaluators (274 in-melee self, 37 health-only, 16 charge-and-melee), zero new logic. Expect the harness table-size pins to move again and classify each as a designed delta.
- When he offers a COUNT, verify it against the data with the definition stated and correct it openly with the arithmetic: the bombardment sweep gave 131 typed keys -> 58 unit-side with a real ability row -> 55 after removing the 3 army-bar junctions, where his 57 had removed only one. A count means nothing without its last filter named - say which set you are counting, reconcile the spreadsheet to the corrected figure, and keep rows / entries / keys distinct (the "30 implemented" he remembered was 31 keys, so the remainder was 21 keys, not 25).
- Derive the key list programmatically from the tracker's status rows every round, never hand-type keys; multi-key abilities (base + DLC/summoned twin) collapse to one entry in the existing base/twin grouping. Report rows-vs-entries-vs-keys separately because a tracking file's item count, entry count and key count legitimately differ (69 entries / 73 keys from 72 tracked items in one round).
- A tracker row's status can be re-queued accidentally: when widening rules, check each new rule against the EXISTING standing rules first - army-bar rows are already excluded by an earlier user decision, so a sweep that flags them re-opens settled work (98 rows here).
- Record answers to the tracker as they arrive (one recording child per batch) rather than batching at the end: a context compaction between asking and recording loses the user's answers, and re-asking is the only honest recovery.
- A mid-flight addition to a RUNNING round: STEER the child (`delegate_task action=steer`) with the new requirement AND an explicit "if you have already passed implementation/build, do NOT restart - finish, report, and I will run a follow-up" line. Losing a verified build costs more than a second small round. A child's own build-server process notices are the signal that a steered rebuild actually happened.
- A questionnaire batch can TIME OUT with every item unanswered. Do not re-send the same form: say once that the questions still stand, and offer the annotated-file route instead (one markdown document, every item with a blank `Your ruling:` line). Five long items is a heavy sitting; the file is read at the user's own pace and returned in one pass.
- AUDITING EXISTING LOGIC AT SCALE (after the roster is built, before trusting any of it): slice the whole table into parallel batches that audit identically, and require from each a `## FLAGGED` section (one block per failure: name, key, current logic, what the game declares, why it makes no sense, feasibility) plus a `## CLEAN` list naming every entry judged sound - the CLEAN list is what proves nothing was skipped, and the user asks for that specifically. Three questions per entry, all answerable from `unit_spec_abil.tsv` / `phase_junc.tsv` / `phases.tsv`: does the mod's CAST TARGET match who the game declares the ability may target (`target_self` / `target_friends` / `target_enemies` / `target_ground`); does the TRIGGER fit the effect (a pure heal needs no melee gate, a charge effect must involve charging, an enemy debuff needs an enemy present); is the trigger ACHIEVABLE with the reads we actually have. The classes that fall out are stable and worth naming in the report: enemy-aimed cast on self, ally-targeted cast on self, ground-targeted sent through the unit form, heal gated behind melee, charge component on a melee-only trigger, engine-refused self cast. Implement class by class, and check each class against the standing rules (army-bar rows are already decided - do not re-queue them).
- Each new class rides the previous class's mechanism: once enemy targeting worked for one ability, the rest of that class was a pure data append on the same evaluator, and ally-targeted abilities ride the existing ally picker - selecting the LOWEST-health ally for a heal, the HIGHEST-hit-point ally when the effect charges the recipient a cost, and a class-gated ally (beast / monster / war machine / construct / missile-capable / morale-broken) by deriving the unit-key list from the game's own tables, never by guessing from the name.

- NEVER present a mechanism you have not verified. Work has been stopped mid-round twice over a confident-sounding explanation: one built from a data column's NAME (its meaning was actually the opposite of the guess), and one generalised from a single log line while the majority of lines showed the opposite. - Two-return engine reads (`Position()` -> x,y) must be captured in ONE pcall: `local ok,a,b = pcall(fn)`. A single-value read helper (`function read1(fn) local ok,v=pcall(fn); return v,true end`) silently returns the ok-flag as the SECOND coordinate, so `local px,py = read1(...)` logs `py=true`.

Keep a manual `zz_probe_<x>_arm(seconds)` hook for a re-run, callable from the console BEFORE hovering; automatic arming is the primary path.
- Change-only logging is what makes a 4 Hz walk of a 600+ component HUD readable: give every component that HAS text (GetStateText/GetTooltipText) - or whose id names a stat/tooltip - a signature, keep the previous signature per component, and log a line ONLY when it is NEW or CHANGED (include the previous text). - ComponentMouseOn / ComponentMouseOff are NOT delivered for arbitrary components: a component only fires them AFTER AddScriptEventReporter() has been called on it (the main mod's README round 24 + its own log prove it: it called the reporter on the ability button before hearing the mouse; a bare listener hears nothing).
